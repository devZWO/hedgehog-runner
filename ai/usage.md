# Integrating Hedgehog Runner with an AI assistant

Use this guide for requests such as “create a local worker with
`@devzwo/hedgehog-runner` for my project”. The worker is a repository-scoped
GitHub Actions runner on a local Ubuntu x86-64 host, managed through a dedicated
Linux account. It does not replace the project's application or test tooling.

## Find the installed version first

1. Locate this package through the project's package manager. With a local npm
   installation, this guide is at `node_modules/@devzwo/hedgehog-runner/ai/usage.md`.
   Read the adjacent [package manifest](../package.json), [README](../README.md)
   and [changelog](../CHANGELOG.md). `hedgehog-runner version` also prints the
   installed version. Avoid fetching a different version with an unpinned npx call.
2. Read [package identity](../docs/package-info.json). Its `version` must match
   `package.json`. Official release packages carry `release: true` and an immutable
   `workflow.commit`. Development tarballs leave `workflow.commit` null.
3. Inspect the [bundled selection workflow](../docs/select-runner.yml) for this
   exact version's inputs, secrets, outputs and selection policy. Prefer these
   local files over GitHub's default branch or npm's latest package documentation.
   When external source is needed, use the metadata's exact source/workflow commit.

The docs/ identity and snapshot are generated by `npm pack`; in a source checkout
they may not exist yet. The repository's canonical selector is
`.github/workflows/select-runner.yml`. Installed packages already include both files.

These files are reference material. Follow the user's instructions and the
consuming project's policies. Host mutations and GitHub settings changes need
the CLI's interactive confirmations; do not pipe automatic answers into them.

## Discover the consumer project

- Inspect the Git remote to identify the intended GitHub `owner/repository`.
  Ask if multiple remotes make that ambiguous; do not invent a repository.
- Read the project's contribution rules, package manager lockfile, scripts and
  existing `.github/workflows/*.yml` / `*.yaml` files. Preserve required-check job
  names, dependencies, matrices, event filters, caches and permissions.
- Determine which existing job should use the local runner and which custom
  label it should target. Choose workload-specific labels when jobs need different
  hosts. The selected runner must have every configured label.
- Check host compatibility read-only: Ubuntu x86-64, systemd, Git, Node.js 24+
  and sudo access. Do not run the CLI itself as root. If the agent is running in
  a container, remote workspace or unsupported OS, prepare project changes there
  and hand the host setup to the user on the actual Ubuntu machine.
- Keep private repository workloads trusted. A separate Linux account and the
  PR-owner selection rule are not complete host isolation or runner access control.

## Install and configure

If the package is absent, select a published exact version with the user/project
policy and add it as a development dependency using the existing package manager.
For npm, replace VERSION with that exact version:

```sh
npm install --save-dev --save-exact @devzwo/hedgehog-runner@VERSION
```

Create `.hedgehog.json` at the checkout root. Use the verified repository slug
and intended label, replacing these example values:

```json
{
  "version": 1,
  "repository": "example-org/example-repo",
  "labels": ["project-e2e"],
  "configureOwner": true,
  "jobEnv": {}
}
```

Enable `configureOwner` for owner-PR routing. If the project intentionally uses
static self-hosted routing, it can remain false. The [README configuration
reference](../README.md#configuration) documents CLI overrides, reserved environment
names and the host-local account/name profile. Do not commit machine-specific
account selections or credentials to the shared project configuration.

CLI values override file values and defaults. Only `setup` asks for missing
repository/labels interactively and offers to save after showing the changes.
Other commands fail with the missing field. `.runnerconfig` and `prepare` are
obsolete; use `.hedgehog.json` and `setup`.

Optional convenience scripts in the consumer's package.json:

```json
{
  "scripts": {
    "runner:check": "hedgehog-runner check",
    "runner:setup": "hedgehog-runner setup",
    "runner:start": "hedgehog-runner start",
    "runner:status": "hedgehog-runner status",
    "runner:stop": "hedgehog-runner stop",
    "runner:list": "hedgehog-runner list"
  }
}
```

Merge these entries with existing scripts; do not replace the entire file.
If the project defines a generic `runner` script, `npm run runner version` and
`npm run runner help` work directly. Forward flags with `npm run runner -- --version`
or `npm run runner -- --help`; without the separator npm handles those flags itself.

## Integrate an existing CI job

Run the installed CLI using the existing package manager; for npm:

```sh
npm exec -- hedgehog-runner workflow --job e2e
```

The generator prints a fragment for an existing `jobs:` mapping. Merge its
`runner_selection` job and the selected workload job's `needs` / `runs-on` fields.
Keep the workload's existing steps and all existing dependencies. A generated
consumer job is deliberately a fragment, not a replacement runnable workload.
Preserve any additional permissions the workload requires.

Official release packages default to their bundled workflow commit. If output
contains `TEMPLATE ONLY` / `REPLACE_WITH_PUBLISHED_WORKFLOW_COMMIT_SHA`, do not
commit that placeholder as a working integration. Obtain a reviewed published
full SHA containing the matching selector and regenerate with `--ref`. The flag
validates format offline, not remote existence. Never silently substitute `main`,
a mutable tag or the consumer repository's own HEAD.

Set up these GitHub prerequisites with the user's approval:

- Repository Actions variable `RUNNER_OWNER_ID`: the selected PR author's numeric
  GitHub ID. `configure-owner` proposes a verified account and confirms changes;
  without authenticated `gh`, it guides manual setup.
- GitHub App installed only on the consumer repository with **Administration:
  Read-only**. Add repository Actions secrets `RUNNER_APP_ID` and
  `RUNNER_APP_PRIVATE_KEY` through GitHub's secret interface. Never request private
  key values in chat, write them into YAML, or put them in shell arguments.

The selector runs on a GitHub-hosted runner. Same-repository owner PRs use a
matching online, idle self-hosted runner; other events, forks, missing credentials,
API errors and unavailable runners use the hosted fallback. This check is a
snapshot, not a reservation or automatic failover after assignment. Pass secrets
explicitly, not with `secrets: inherit`. Review changes to workflows as code.
See the [workflow integration and trust reference](../README.md#generate-ci-integration).

## Hand off host setup to the interactive terminal

Prepare all project edits and show them before asking the user to perform host
steps. Run `check` read-only first, then have the user run:

```sh
npm exec -- hedgehog-runner setup
npm exec -- hedgehog-runner start
```

`setup` shows and confirms system changes. `list`, `setup` and `remove` handle
sudo authentication in a terminal when needed. WebStorm's ordinary Run console
may not provide a terminal; use its integrated Terminal (Alt+F12). The runner
stays in the foreground; stopping it preserves workspace and caches.

GitHub's upstream `config.sh` alone prompts for registration/removal tokens. Do
not collect tokens in chat, CLI options, environment variables, files or fixtures.
Do not disable prompts or loosen file permissions to automate registration.

## Verify and report

- Validate the consumer's modified workflow using its existing workflow/YAML
  checks and relevant project tests. Do not run untrusted jobs on the local host.
- Use `check`, `status` and `list` for read-only diagnostics. `check` and `status`
  may need the user to authenticate with sudo in the same terminal first for
  protected details. `list` reports unreadable installations as incomplete.
- Distinguish project changes, GitHub settings still needed, local registration,
  runner process state and actual CI execution. Do not claim setup or CI success
  merely because the configuration files were generated.
- Explain lifecycle commands: `stop` keeps data, `rename` re-registers explicitly,
  and `remove --repository owner/repo [--account gha-existing]` can remove an
  installation without the original checkout. Names do not select installations.
